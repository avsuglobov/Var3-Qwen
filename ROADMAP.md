### Приоритет 1 — входящие каналы (21–23)

**Этап 21 — Email-интеграция (IMAP/SMTP)** — первый кандидат на старт.
- Библиотеки: `imapflow` (чтение почты), `nodemailer` (отправка).
- Настройки → Интеграции → Почта: аккаунты (IMAP/SMTP хост, порт, TLS, логин), пароли в secrets.json, кнопка «Проверить соединение».
- Входящие: фоновый опрос с настраиваемым интервалом; раздел «Входящие письма»; статусы (новое / в работе / обработано); привязка письма к лиду/диалогу.
- Исходящие: ответ из карточки письма; черновик, сгенерированный AI; отправка через SMTP (адаптер этапа 20).
- AI-функции: саммари треда, классификация (спам / продажи / поддержка), черновик ответа в заданном тоне.
- **Заложить на этом этапе общий интерфейс `ChannelAdapter`** — единая модель «входящих» для email/telegram/будущих каналов (сэкономит работу на этапе 22).
- Ключевые решения предложить пользователю при старте (дефолты, не молча): интервал опроса, какие папки IMAP читаем, лимиты на размер письма/вложения.
- Гейты: unit с моками IMAP/SMTP (без сети), `npm run check`, `npm run build`, целевой e2e, PR `feat/stage-21`.

**Этап 22 — Мессенджеры (Telegram)**
- ChannelAdapter из этапа 21 → подключение Telegram Bot API (webhook или long polling — решение при старте).
- Токен бота в secrets.json; единый инбокс с фильтром по каналу; статусы и привязка к лидам как у писем.

**Этап 23 — События и уведомления**
- Внутренняя шина событий: `lead.created`, `task.due`, `email.received`, `ai.reply.ready`.
- Центр уведомлений в UI (колокольчик); доставка: email (через SMTP этапа 20), webhook, опционально push.
- Подписки по пользователю/роли.
- **Кросс-срез** (затрагивает все разделы) → полный e2e обязателен.

### Приоритет 3 — платформа (27–30)

**Этап 27 — Автоматизации (workflow)**
- Правила «триггер → условие → действие» (примеры: новое письмо от неизвестного отправителя → создать лида; задача просрочена → уведомить менеджера).
- Планировщик (cron); конструктор правил в Настройках.
- Требует шину событий этапа 23 — без неё правила нереализуемы.
- **Кросс-срез** → полный e2e обязателен.

**Этап 28 — Открытый API**
- API-ключи на пользователя; REST API v1 для внешних систем; исходящие вебхуки; rate limiting; журнал аудита.
- **Кросс-срез** (публичная поверхность) → полный e2e обязателен.

**Этап 29 — Безопасность и эксплуатация**
- 2FA (TOTP); UI управления сессиями; резервные копии `.data/` по расписанию; Docker Compose уже с этапа 19 — расширить health-check.

**Этап 30 — Голос и мультимодальность (опционально)**

## Логика порядка
1. Email → мессенджеры: единая модель каналов (`ChannelAdapter`) строится на этапах 21–22, дальше новые каналы дёшевы.
2. События (23) — фундамент автоматизаций (27): без шины событий правила не реализуемы.
3. API (28) открывает экосистему интеграций извне, аудит-лог закрывает требования безопасности.
4. Голос/мультимодальность — последними: наименее критичны для CRM-сценариев.

## Правила работы (краткая выжимка, полная — в continuation-prompt.md)
- Ветка `feat/stage-N` от свежего `main`; гейты каждого этапа: `npm run check` (главный барьер), `npm run build`, целевой e2e. Полный e2e — только на кросс-срезах (21–22 по решению, 23, 27, 28) и отмечать в PR, если отложен.
- e2e не зовут реальный LLM: провайдер в тестах — заглушка; в браузере не должно быть 4xx.
- Язык всего — русский (код-комментарии, коммиты, PR, отчёты). Честность: непроверенное не выдавать за проверенное; секреты в браузер — только маска «••••последние 4».
- Push/PR — один раз в конце этапа. Токен GitHub: использовать подключённый GitHub-плагин, если доступен; иначе запросить свежий PAT у пользователя (inline в URL push, не сохранять в конфиг/скрипты).
- После каждого этапа: инкремент счётчиков в `web/README.md` и `MIGRATION.md`, пункт `[x]` в чек-листе, **обновить строку статуса и PR в таблице этого файла**.
- Ключевые решения каждого этапа предлагать пользователю при старте с дефолтом, не молча вбивать.
